# PEAR 2 implementation plan

## Objective

Build a separate backend that reads the canonical, **untyped AIR 2.x text** emitted by `pfrontc --emit-air` and emits LLVM bitcode (`.bc`). PEAR 2 is not `air_ll`, not PEAR 1, and not part of `pfrontc`. It must operate solely on the AIR file and its own documented runtime/target inputs.

Pride is untyped by design. AIR may carry optional type hints, but PEAR 2 must not require complete source type inference. Where machine representation is needed, PEAR 2 must infer it from AIR operations, ABI declarations, and optional hints under explicit rules; ambiguity must be diagnosed rather than silently guessed. Default scalar and ABI rules must be specified in the AIR/PEAR contract, not invented ad hoc in the backend.

## Non-goals

- Do not make AIR 3's typed low profile the PEAR 2 input contract.
- Do not consume PNode, compiler internals, or side-channel metadata from `pfrontc`.
- Do not reuse PEAR 1 as PEAR 2's implementation. PEAR 1 may be used as a differential oracle on cases it handles.
- Do not claim language support because the parser accepts a form or the emitter prints it.

## Architecture

`pfrontc` → canonical `.air` → PEAR 2 reader/validator → AIR semantic analysis and representation inference → PEAR IR → AIR optimization (tiered) → lowering → LLVM module → LLVM IR optimization (tiered, in process) → verified `.bc`.

The PEAR 2 executable must:

1. Read only `.air`; reject malformed/unsupported versions and invalid AIR.
2. Re-check all backend-relevant invariants, including name binding, control-flow targets, ABI, and machine representation. AIR claims are untrusted input.
3. Fail closed: unsupported or ambiguous constructs produce a diagnostic, nonzero exit, and no output artifact. A stale artifact must not survive failure.
4. Write LLVM bitcode atomically. Verify the LLVM module before publication.
5. Be deterministic for a fixed AIR file, target, and optimization level unless the contract explicitly permits nondeterminism.

Shared AIR reader/verifier code may be linked as a library. The backend itself remains a separate executable and process.

## Milestones

### M0 — Contract and executable boundary (bootstrap slice implemented)

- Record the target architecture, file format, constraints, and acceptance gates.
- Add a standalone `pear2c` command and an independently runnable test target.
- Initial vertical slice: zero-argument `main` returning an integer literal, with a verified LLVM bitcode artifact.
- This slice is a bootstrap probe, not a claim that AIR or PEAR 2 is complete.

### M1 — Scalar lambda-bar/mu-mu-tilde fragment (in progress)

Implemented scalar slice: i8/i16/i32/i64/i128, char, f32/f64, bool, opaque pointers, and unit returns; integer/floating arithmetic and comparisons; integer, float, bool, and pointer coercions; `mu~`, `comu`, `let`, direct calls, returns, and source-order evaluation. Unannotated internal definitions now infer simple return representations from direct returns, `if`/`match` branches with a common result, and annotated parameters; untyped integer expressions use the function's default integer width. If this limited analysis cannot establish a result, it falls back to signed i64. An omitted/infer parameter uses an explicit integer result type when available, otherwise signed i64. External scalar declarations still require explicit scalar ABI types; by-value aggregate declarations are covered by the M3 subset below. Narrow i8/i16 ABI values use signext/zeroext; unsigned operations select unsigned LLVM opcodes. Remaining work includes body-driven inference/overflow/division rules, target-specific ABI verification, and differential runtime tests.

### M2 — Control flow (partial; in progress)

Implemented subset: local nested tuple/fixed-array construction, constant aggregate projection, recursive bind/wild/trailing-rest aggregate patterns, scalar literal or-patterns and aliases plus one-arm aggregate aliases, and fixed-byte literals; internal direct-call tuple/array arguments and returns; aggregate label/jump parameters; terminal `if`/`else`; integer/boolean/char `match` lowered to LLVM `switch` with a required final default arm; f32/f64 matches use ordered equality tests; scalar guarded matches route boolean guard commands through the implicit `%guard` continuation, preserving ordered tests and guard-false fallthrough for the command forms PEAR2 lowers; tuple/array bind/wild destructuring arms can use guards with ordered fallthrough; structured `while` loops with header, body, exit, and backedge blocks; and bounded `for` iteration over fixed arrays, including nested loops, with stack save/restore around temporary aggregate copies. Label arguments use typed entry-block allocas and loads rather than SSA phi nodes. Locals captured by named labels are also spilled to typed slots; repeated bindings store to those slots, so label/jump backedges carry mutable local state without SSA phi nodes. Boolean `mu`/`case` continuations lower the true/false loop branches. This covers `p04_loop_sum` and `p07_mut_reassign`. Outstanding: whole-CFG reachability/termination validation, phi promotion, literal/nested aggregate guards and constructor patterns, and broader loop/control-flow coverage; `break`/`continue` transfers are currently limited to captured zero-parameter labels.

### M3 — Data and ABI (scalar and narrow product-aggregate ABI slices implemented)

Implemented narrow scalar C ABI support for i8/i16/i32/i64/i128, f32/f64, char, bool, opaque pointers, and unit/void returns. Internal definitions additionally support tuple/fixed-array aggregate parameters and returns, including empty tuples and unit fields/parameters: LLVM arrays and literal structs pass and return by value under the default `ccc` convention; a unit value occupies an empty `{ }` struct in value/field/parameter positions, while a unit function result uses `void`. External declarations support scalar ABIs plus by-value non-empty tuples and plain nominal product records whose fields have C-compatible LLVM layouts; bool/unit aggregate fields are rejected, and conflicting C symbol ABIs are rejected. The aggregate interoperability fixture is verified on x86-64 Linux with LLVM 23, not claimed cross-platform. Numeric coercions include integer width changes, signed/unsigned integer↔float conversion, f32/f64 widen/narrow, pointer↔integer conversion, and bool/integer conversion. Integer arithmetic uses width/signedness-selected LLVM operations; floating arithmetic/comparison has explicit opcodes. AIR 2 pointer memory covers bool, integer, float, pointer, and small nested-array values with 1/2/4/8-byte widths and `align 1`; integer stores explicitly truncate or extend to the destination width, while untyped integer constants must fit. AIR 2 pointer indexing supports dynamic signed/unsigned indices with width conversion; fixed-array values are bounded to 1,024 elements. The fixture-backed AIR 3 low-profile subset separately lowers typed globals (including `extern`/`link` names), constant initializers, pooled string/byte constants and pointer decay, typed stack allocation, bounded constant-size heap allocation and base-only free, typed loads/stores, and constant typed GEP with alignment and provenance checks; unsupported dynamic memory forms fail closed with source positions. Scalar and fixed-array `sizeof`, supported scalar/empty-aggregate `alignof`, assertions, assumptions, and traps are lowered. Called varargs, fastcc, attributed, generic, multi-constructor and packed data declarations, and external aggregates with unsupported field layouts fail closed. Outstanding: a general pointer ownership/lifetime model beyond the bounded AIR 3 provenance rules, sum/data constructors and patterns, record patterns, general target data layout, cross-target ABI verification, and broad C ABI interoperability. LLVM 23 bitcode parsing/verification and native execution are demonstrated for the listed subset; the narrow C aggregate fixtures do not establish broad C ABI interoperability.

### M4 — Closures, general data types, effects, staging

Implement each feature only after its AIR representation and semantics are complete. The simple product-record slice in M3 does not include sum constructors, general pattern matching over records/data, or generic data types. For effects, specify continuation semantics and runtime requirements (one-shot/multi-shot, target support); for staging, specify residualization. Unsupported forms remain hard errors until implemented.

### M5 — Optimization (three conservative AIR passes plus in-process LLVM IR passes; validation incomplete)

`pear2/pear2_opt.c3` currently removes same-representation integer/bool/float coercions and folds checked integer and boolean/integer constant coercions plus add/subtract/multiply/divide/remainder, bitwise operations, and in-range shifts (arithmetic versus logical right shift follows signedness); rewrites typed multiplication by a positive power-of-two constant on either operand side to a same-width left shift, unsigned division by a power of two to a logical right shift, signed division by a positive power of two to an arithmetic shift with truncation bias for SSA-variable dividends, signed remainder for SSA-variable dividends by a positive power of two via the truncating quotient, and unsigned remainder by a power of two to a bit mask, remainder by one and multiplication by zero to input-preserving zero-mask `AND` operations, using fresh AIR literals where needed; combines nested same-kind shifts when both counts and their sum remain below the resolved width; folds integer comparisons and unary signed negation/bitwise-not/boolean-not, and cancels double-not only when the inner and outer representations agree; reassociates `(x op c1) op c2` into `x op (c1 op c2)` for `+`/`-`/`*`/`&`/`|`/`^` when the folded constant still fits the operand width (integer arithmetic is wrapping here, so regrouping the constants cannot change trap behaviour); decides an operation whose two operands are the same pure expression (`x - x`, `x ^ x`, `x & x`, `x | x`, and a value compared with itself), each of which requires an integer or boolean ascription because an untyped `(sub a b)` spells float subtraction and `a - a` is NaN there; applies representation-compatible integer identities including typed all-ones `AND`, multiply-by-all-ones to negation, integer `XOR`-to-bit-not rewrites, and zero-valued `OR`/`XOR` identities in either operand order; boolean `XOR true` becomes `NOT`, logical `LAND true`/`LOR false` identities retain the other operand, and equality/inequality with literal booleans reduces to the value or `NOT`; selects literal-boolean `if` branches, specializes a folded boolean `let` inside its immediate pure `if` condition and propagates integer constants through one immediate nested pure integer-let initializer or into an immediate pure return/cut expression, retaining both bindings for any other uses. A second pass then runs over the folded module and deletes an `ACMD_LET` whose value is inert (a literal, unit, null, or a variable) when its name occurs nowhere in the body. A third family of rewrites works on the same census: pass 3 propagates a *binding* rather than a literal (`let x = y in body` becomes uses of `y` when the census proves `y` appears in no binder position in `body`, which is the copy propagation the emitter cannot perform because there `let x = y` snapshots a load) and folds a one-armed unguarded `match` -- `match s { _ -> body }` to `body` when the subject is pure, and `match s { bind x -> body }` to `let x = s in body`, which keeps the subject's evaluation position and hands the result to the propagation above. The transform requires the name to be absent from every position in the body — uses, binders, match-pattern binders, covariables, labels, jump arguments, substitution entries, and the names carried by non-variable producers — so the guard is name-absence-elsewhere rather than a use count and cannot be defeated by shadowing; because only inert values qualify, deleting a binding can never discard work. Copy propagation is deliberately excluded: mutable locals are allocas, so `let x = y` snapshots a load and renaming the uses would re-load the slot, and an alias costs no instructions anyway because the emitter binds AIR names to SSA values. Pass 3 substitutes constants only, which is the case where the snapshot cannot be observed. Rewrites preserve product identity/type metadata, respect signed/unsigned comparisons and narrow unsigned complement, reject host overflow, incompatible operand representations, out-of-range constants, divide-by-zero, signed minimum divided by negative one, and unrepresentable narrow results. After optimization, PEAR2 refreshes AIR facts and re-runs the AIR verifier; the tier selects which passes run and then how far they iterate. `-O1` runs pass 1 once; `-O2` enables pass 2 and iterates the pair up to four times; `-O3` additionally enables pass 3 — the first whole-body analysis in the pipeline — and iterates up to eight times; `-Os` runs the `-O2` AIR tier unchanged and leaves the size decision to the LLVM pipeline; iteration stops as soon as a pass reports no rewrites; `-O0` disables AIR rewriting and LLVM IR optimization entirely. Pass 3 counts binder positions for the whole function body, once, and spends that census on two rewrites: it substitutes a literal at *every* use of a name the census proves is bound nowhere else and never used as a jump argument (so downstream folding sees constants two or more constructs below the binding, which pass 1 cannot reach), and it removes an unused binding whose initializer is `pure` rather than `inert`. Pure means the initializer cannot call, allocate, touch memory, or trap, so discarding it is unobservable: arithmetic, comparisons, coercions, bit/boolean unary and binary operations, and tuple or array construction qualify, while division and remainder do not because `div x 0` faults and deleting a trapping expression would turn a crash into a silent result. The substitution is type-checked per use rather than per binding, so an integer literal only replaces a use whose resolved width and signedness match or that the literal fits. The same census and purity test drive a scoped value table: a let whose pure value is structurally identical to one an enclosing let already bound is emitted as a reference to that name instead of being rebuilt, and the table is save/restored around every descendant scope so a shadowing binder cannot be confused with the outer one. The same pass folds control flow that a literal already decides, which is the part of a dataflow pass that does not need the dataflow: a `while` whose condition is the literal `false` is replaced by a no-op because the body cannot run, a `match` whose subject is an integer, boolean, or character literal is replaced by the first unguarded arm whose pattern matches that literal, and the tail of a sequence after an unconditional transfer is dropped. Guards, binding patterns, non-literal patterns, and cobranches stop the fold instead of guessing, because each of them needs the subject's value or introduces a name at run time. The same block drops the unreachable remainder of a sequence after an unconditional transfer, reduces a sequence with a `nop` on either end to its live half -- the shape the loop fold itself produces -- and unwraps a block whose body is a single command. This is the pass that makes `-O3` a different *set* of passes rather than the `-O2` set repeated more often. `--stats` exposes passes, total rewrites, categorized fold, operand, strength-reduction, shift-combination, branch, and let-specialization counts, the pass-2 dead-binding count, the pass-1 reassociation and self-fold counts, the pass-3 propagated-constant, pure-dead-binding, CSE, eliminated-loop, literal-match, dead-command, folded-match, and propagated-copy counts, and the selected LLVM pipeline (`pipe=none|O1|O2|O3|Os`). A standalone structural harness covers same-representation integer/bool/float coercion elimination and signedness rejection, typed identities including boolean `XOR true` polarity and left/right zero-operand cases, multiply/divide/modulo power-of-two strength reduction including signed truncation-bias division/remainder, negative-divisor and computed-dividend rejection, input-preserving remainder-by-one and multiply-by-zero, and signed/non-power-of-two rejection, signed/logical/left shifts, boolean and integer let specialization (including nested pure integer-let initializers), comparison/branch choice, unary folds and double-not type mismatches, narrow overflow/division hazards, mixed widths, and out-of-range constants; backend fixtures check `-O0`, `-O1`..`-O3` output, stats, and fixed-point convergence. `make check-pear2` automates C3 check-only validation of the backend and structural harness without LLVM and runs an independent exhaustive/sampled signed-division formula test. In this environment `make test-pear2-exec` and `make test-pear2` both pass with the documented LLVM 23 toolchain. The broader AIR/CLI suite reports 76 successful checks, including internal tuple/array ABIs, empty tuple/unit aggregate calls, and execution of both aggregate-ABI programs. On top of the AIR passes, the producer runs LLVM's own optimizer in process: at `-O1`, `-O2`, and `-O3` it calls `LLVMRunPasses` with `default<O1>`, `default<O2>`, or `default<O3>`, or with `default<Os>` for the size tier (inliner threshold 250) on the module it just parsed, so mem2reg/SROA slot promotion, instcombine, GVN, inlining, loop optimisation, and IR-level dead-code elimination happen inside PEAR 2 rather than being left to a downstream toolchain. PEAR 2 is alloca-heavy by construction — label arguments lower to typed entry-block slots rather than SSA phi nodes — so slot promotion is where most of that gain comes from. This layer is deliberately not a substitute for the AIR passes: it runs after the AIR optimizer has already been re-verified, and the module is verified again as LLVM IR immediately before serialisation, so a producer bug surfaces as a verification failure rather than being hidden by the LLVM pipeline. At `-O0` neither layer runs and the bitcode is exactly what PEAR 2 lowered, which keeps the producer independently auditable. Recursive local bindings (`letrec`) are lowered by the same lambda-lifting path that first-class closures use, with one restriction the lifting makes necessary: a member of a group may not capture, because its own closure value does not exist while its body is emitted, so there is no environment slot to load an enclosing binding from (`pear2/pear2_letrec.c3`). Groups are planned before any member is rendered -- members in rounds, so each round that resolves a name unblocks the members that call it -- which is what makes mutual recursion expressible; while a group is being planned its names live in a scoped table that the type inference consults, and inside a lifted member a group name denotes the constant closure `{ @symbol, null }`, which LLVM folds back into a direct call. A call whose continuation is the function's own return covariable is emitted with LLVM's `tail` marker, so a recursive binding reuses frames instead of growing the stack. Linkage is part of this layer: a definition or global that is not `pub`, is not `main`/`pride_main`/`_start`, and carries no `export` or `section` attribute can only be named from inside the module, so it is emitted with `internal` linkage and LLVM is free to inline it everywhere and delete the out-of-line body when nothing calls it. `--emit-exe`, where PEAR 2 performs the final link itself, enables this by default; `--internalize` and `--no-internalize` override it in either direction; `--emit-bc`, `--emit-obj`, `--emit-asm`, and `--emit-ll` keep external linkage by default because a published object may be resolved by a name PEAR 2 cannot see. A symbol named only by inline-asm text must therefore be `pub` or `#export`ed. `--stats` reports the effective policy as `linkage=internal|external`.

This is groundwork, not a completed optimizer: translation-validation or broader differential tests and a semantics audit are still needed before adding aggressive data-flow transformations. In particular there is still no CFG analysis, so there is no real inlining, no common-subexpression elimination, and no redundancy elimination at the AIR level.

### M6 — Release criteria

- Zero known AIR validity violations in the supported source corpus; exact fixture-ledger checks.
- AIR writer/reader structural round-trip across the corpus.
- Source → AIR → PEAR 2 → `.bc` → LLVM verify/run agrees with expected behavior for every supported case and optimization tier.
- Every unsupported source construct is rejected before a misleading `.air`/`.bc` artifact is published.
- Cross-target and ABI tests for every claimed target; determinism and stale-artifact tests.
- PEAR 1 differential results are supplemental; expected outputs and semantic tests are authoritative.

## Completion-size estimate

These are planning ranges, not a line-count acceptance gate. The current PEAR 2 driver is about 3,000 lines and implements the narrow, fixture-backed scalar/control-flow/aggregate/memory subset described below. For the full AIR 2.x backend scope in M0–M6, a reasonable estimate is **18K–25K lines of production PEAR 2 code**, excluding the shared AIR reader/verifier and excluding tests. The approximate allocation is: representation inference and backend validation 2K–4K; LLVM module/CFG/SSA and scalar lowering 4K–6K; data layout, memory, and ABI 4K–6K; runtime/effects/staging support 3K–5K; optimizer and target/driver infrastructure 3K–4K. A meaningful fixture, differential, and end-to-end test suite could add another 8K–15K lines, depending on how much source corpus and generated test data is checked in. These ranges assume unsupported language/runtime semantics are specified rather than hidden behind a code-size target. A count above 15K alone would not mean the backend is complete.

## Current bootstrap boundaries

`pear2/pear2c_main.c3` supports signed/unsigned integer arithmetic through i128, f32/f64 arithmetic/comparison/conversions, Unicode scalar chars, bools, opaque pointers, and unit values. It lowers internal scalar, tuple/fixed-array, and simple record function ABIs; tuple/array/record values can cross internal direct-call edges, and tuple/array values can also cross label/jump edges. Plain non-generic, non-packed, single-constructor records support typed `record` construction and `field` projection. External C functions additionally accept/return non-empty tuples and simple records by value when their fields use a conservative C-compatible representation. Local aggregates support nested tuple/array construction, tuple projections, array indexing/projection, recursive bind/wild patterns with trailing rest, and fixed i8 byte/string literals with optional NUL/zero fill. Fixed arrays are bounded to 1,024 elements (recursive patterns retain the parser's branch/element bounds). Pointer memory supports typed loads/stores for bool, integer widths through 64, f32/f64, pointers, and small nested arrays; integer stores truncate/extend to the requested pointee width, while untyped constants must fit. `index` width is limited to AIR's 1/2/4/8-byte forms. Dynamic indices are converted to i64 with signed/unsigned extension or truncation. Integer↔float, f32↔f64, pointer↔integer, and integer↔bool coercions are explicit; float↔bool remains unsupported. Scalar/fixed-array `sizeof`, supported scalar/empty-aggregate `alignof`, `assert`, `assume`, and `trap` lower to LLVM.

The AIR 3 low-profile path additionally lowers typed globals with constant initializers and external `link` names, pooled string/byte constants, pointer decay through constant GEP, typed stack allocation, positive constant-size `malloc` up to 1 MiB, live-base `free`, typed loads/stores, and constant typed GEP. It tracks allocation extent, offset, alignment, writability, freed state, and stored pointer-cell provenance; freeing an allocation invalidates tracked aliases recovered from pointer cells. Unknown/dynamic GEP or heap-size forms, out-of-bounds/misaligned access, use-after-free, interior/double frees, and writes through immutable globals fail closed with source-located exit-3 diagnostics. This narrow slice is covered by `global_string_main.air`, `typed_memory_main.air`, `typed_pointer_cell_main.air`, and the AIR 3 `reject_*.air` fixtures.

External C signatures support scalars plus a conservative by-value aggregate subset: non-empty tuples and plain, non-generic, non-packed single-constructor product records with C-compatible fields. AIR bool/unit aggregate fields, multi-constructor data, packed/generic records, and record-pattern matching remain unsupported. Other unsupported declaration forms, indirect calls, unsupported pointer widths/layouts, guarded aggregate/constructor matches, parameterized `break`/`continue` targets, jumps/labels in functions that use `for` (to preserve stack restoration), transfers out of a `for` body, and incomplete CFG shapes fail closed. `main` must remain zero-argument i64. AIR machine forms are lowered: `fence` with acquire-or-stronger orderings (the AIR verifier holds the ordering law), `atomic` read-modify-write, loads, stores, and `cmpxchg` over AIR 3 typed integer pointees of 8/16/32/64 bits (cmpxchg takes the AIR ORDER as its success ordering and the strongest ordering that permits on failure — release/acq_rel degrade to monotonic/acquire — yields the old value per AIR3.md, and release/acq_rel loads and acquire/acq_rel stores still reject with positions), raw x86-64 Linux `syscall` through pinned-register inline assembly (denied under the freestanding wasm32 profile), and inline `asm` in the AIR 3.0 template/constraints/result form over integer, float, or pointer operands with scalar or unit results (bool results fail closed). Arithmetic is emitted without `nsw`/`nuw`; the backend does not yet define a complete cross-target integer/layout contract. It invokes LLVM parse/verify/bitcode APIs in normal builds and publishes output atomically. In this environment, the LLVM-enabled build uses C3 0.8.4 and LLVM 23.1.3 runtime tools; `make test-pear2` and `make test-pear2-exec` both pass, including native execution of mutable-loop, internal aggregate ABI, and narrow x86-64 external aggregate ABI fixtures. Cross-target and broad external C ABI interoperability remain unverified.
